# แผนรื้อโครง: แยก Master Data ออกจากการจัดก๊วนรายวัน

สถานะ: **ร่างเพื่อขออนุมัติ ยังไม่เริ่มเขียนโค้ด** — ลงวันที่ 2026-09-12

ข้อตกลงตั้งต้น (จากการคุยกัน):
- ล้างฐานข้อมูลเก่าทิ้งได้ ไม่ต้องรักษาข้อมูลเดิม → เขียน `supabase/schema.sql` ใหม่ทั้งไฟล์ ไม่ต้องทำ migration ไล่
- ก๊วนแชร์ให้คนอื่นเข้ามาดูได้
- รายชื่อผู้เล่น (master) เก็บรวมชุดเดียว ไม่แยกตามก๊วน เลือกเอาตอนจัดวันเล่น

---

## 1. ปัญหาของโครงปัจจุบัน

`sessions` ถูกใช้แทน "หนึ่งวันที่ไปตี" แต่ชื่อและ UI เรียกมันว่า "ก๊วน" ทำให้ไม่มีที่เก็บว่า *ก๊วนวันอังคาร* กับ *ก๊วนวันเสาร์* เป็นคนละกลุ่ม และ:

- `members` ผูกกับ `owner_id` ตรง ๆ ไม่มีชั้นก๊วน
- ไม่มี master ของสนามและยี่ห้อลูกแบด ต้องพิมพ์ใหม่ทุกครั้ง
- วันเล่นต้องสร้างตอนจะเล่นเท่านั้น จองล่วงหน้าไม่ได้ (`get_or_create_my_session` สร้างก๊วนที่เปิดอยู่ทันที)
- กฎ "1 user เปิดได้ทีละก๊วน" กลายเป็นข้อจำกัดผิดที่ ที่ถูกคือ "1 ก๊วน มีวันที่กำลังเล่นได้ทีละวัน"

## 2. คำศัพท์ที่จะใช้ (ต้องไม่สับสน)

| คำ | ตาราง | คืออะไร |
|---|---|---|
| ก๊วน | `clubs` | กลุ่มคนที่ตีด้วยกันประจำ อยู่ถาวร |
| วันเล่น | `sessions` | หนึ่งครั้งที่ไปตี มีวันที่ ราคา และยอดที่ freeze ไว้ |
| สนาม | `venues` | **สถานที่** เช่น "แบดมินตันฮอลล์ A" — master |
| คอร์ต | `courts` | **คอร์ตที่จองในวันนั้น** + จำนวนชั่วโมง — รายวัน |
| ผู้เล่น (master) | `members` | ตัวตนข้ามวัน ใช้เลือกตอนจัดวันเล่น |
| ผู้เล่น (รายวัน) | `players` | คนที่ลงชื่อไว้ในวันนั้น เก็บ snapshot ชื่อ/มือ |

> **สนาม ≠ คอร์ต** เป็นจุดที่พังง่ายที่สุด: master เก็บ "ที่ไหน" ส่วนรายวันเก็บ "จองกี่คอร์ต คอร์ตละกี่ชั่วโมง" ซึ่งเป็นตัวคูณค่าสนาม

**ไม่เปลี่ยนชื่อตาราง `sessions`** ทั้งที่ความหมายคือ "วันเล่น" — เพราะ `session_id` ถูกอ้างอิงใน 6 hooks, 9 components และ RPC เกือบทุกตัว การเปลี่ยนชื่อได้ความชัดเจนเล็กน้อยแต่แลกกับการแก้แบบกลไกทั้งโปรเจค ไม่คุ้ม จะใช้คำว่า "วันเล่น" ใน UI แทน

## 3. Schema ใหม่

### 3.1 Master

```
clubs
  id, owner_id → auth.users, name, note, active, created_at, updated_at

club_access                       -- ใครเข้าถึงก๊วนนี้ได้บ้าง (ของใหม่)
  club_id → clubs, user_id → auth.users,
  role: 'owner' | 'editor' | 'viewer',
  unique(club_id, user_id)

members                           -- รายชื่อผู้เล่น รวมชุดเดียวต่อ user
  id, owner_id, name, default_skill 1-3, active,
  unique(owner_id, lower(trim(name)))

venues                            -- สถานที่
  id, owner_id, name, note, court_count,
  default_hourly_rate,            -- ใช้ prefill เท่านั้น ไม่มีใครอ่านตอนคิดเงิน
  active, unique(owner_id, lower(trim(name)))

shuttle_brands                    -- ยี่ห้อลูกแบด ไม่มีราคาตามที่ตกลง
  id, owner_id, name, active, unique(owner_id, lower(trim(name)))
```

`default_hourly_rate` ใน `venues` เป็น **ค่าตั้งต้นสำหรับกรอกให้อัตโนมัติเท่านั้น** ตอนคิดเงินอ่านจาก `sessions.hourly_rate` ที่ copy ลงไปแล้วเสมอ — ขึ้นราคาสนามทีหลังยอดเก่าต้องไม่ขยับ (หลักการเดียวกับ `match_players.player_name`)

### 3.2 รายวัน

```
sessions                          -- = "วันเล่น" หนึ่งแถว = หนึ่งครั้งที่ไปตี
  id, club_id → clubs,            -- ของใหม่
  venue_id → venues (null ได้),   venue_name text,   -- snapshot
  shuttle_brand_id → shuttle_brands (null ได้), shuttle_brand_name text,
  play_date date not null,        -- ของใหม่: จองล่วงหน้าได้
  start_time time, end_time time,
  status: 'planned' | 'playing' | 'done' | 'cancelled',   -- ของใหม่
  hourly_rate, shuttle_price, shuttle_count,
  queue_mode 'sequential' | 'rotate',
  closed_at, final_* (9 คอลัมน์เดิม ไม่เปลี่ยน)

players                           -- คนที่อยู่ในวันนั้น
  ...คอลัมน์เดิมทั้งหมด...
  status: 'waiting' | 'resting' | 'playing' | 'absent'    -- เพิ่ม absent

courts, matches, match_players    -- เหมือนเดิมทุกอย่าง
```

**`status = 'absent'`** คือคนที่ลงชื่อไว้ล่วงหน้าแต่วันจริงไม่มา — ไม่เข้าคิว **และไม่นับเป็นคนหารเงิน** สำคัญมาก เพราะกฎคือหารเท่ากันทุกคนที่*มา* ถ้าไม่มีสถานะนี้ ยอดต่อหัวจะผิดทันทีที่มีคนเบี้ยว

**`venue_name` / `shuttle_brand_name` เป็น snapshot** เหมือน `court_name` เดิม — ลบสนามออกจาก master แล้วประวัติเก่ายังอ่านออก

### 3.3 Index / constraint ที่ต้องมี

- partial unique: `sessions(club_id) where status = 'playing'` → หนึ่งก๊วนมีวันที่กำลังเล่นได้ทีละวัน (แทนกฎ 1 user 1 ก๊วนเดิม)
- `sessions(club_id, play_date desc)` สำหรับหน้ารายการวันเล่น
- partial unique เดิม `matches(court_id) where ended_at is null` — คงไว้
- `players.queue_seq` ยังเป็น `bigserial` ไม่ใช่ timestamp — คงไว้

## 4. RLS กับการแชร์ก๊วน

เดิมทุกตารางเช็ค `owner_id = auth.uid()` ตรง ๆ ใหม่ต้องผ่านสองฟังก์ชันช่วย:

```sql
can_view_club(p_club_id)  -- มีแถวใน club_access
can_edit_club(p_club_id)  -- role in ('owner','editor')
```

- `sessions` / `players` / `courts` / `matches` / `match_players` → อ่านด้วย `can_view_club`, เขียนด้วย `can_edit_club`
- master (`members`/`venues`/`shuttle_brands`) → เจ้าของแก้ได้; คนที่ถูกแชร์ก๊วนมา **อ่านได้** เพื่อเลือกผู้เล่นลงวันเล่น (`has_master_access(owner_id)` = มีก๊วนของ owner คนนั้นที่เราเข้าถึงได้)
- RPC ทุกตัวเป็น `SECURITY DEFINER` → ต้องเรียก `can_edit_club` เองทุกตัว ห้ามลืม (กฎเดิมของโปรเจค)
- view ใหม่ทุกตัวต้องมี `security_invoker = on` (กฎเดิม)

การแชร์: `grant_club_access(p_club_id, p_email, p_role)` มองหา user จากอีเมลใน `auth.users` — ถ้าคนนั้นยังไม่เคยสมัคร จะ error ว่า "ยังไม่มีบัญชีนี้ ให้เขาสมัครก่อน" (ระบบเชิญคนที่ยังไม่มีบัญชีจะไม่ทำในรอบนี้)

## 5. RPC

**ของใหม่**

| ฟังก์ชัน | หน้าที่ |
|---|---|
| `create_club(name)` | สร้างก๊วน + ใส่ `club_access` role owner ให้ตัวเอง (2 ตาราง → ต้องเป็น RPC) |
| `grant_club_access(club_id, email, role)` / `revoke_club_access` | แชร์ก๊วน |
| `create_play_day(...)` | สร้างวันเล่น + `players` จาก member_ids + `courts` พร้อมชั่วโมง ในทรานแซกชันเดียว |
| `last_day_defaults(club_id)` | คืนค่าจากวันเล่นล่าสุดของก๊วน ไว้ prefill ฟอร์ม |
| `start_play_day(session_id)` | planned → playing (ปฏิเสธถ้าก๊วนนี้มีวันที่ playing อยู่แล้ว) |
| `set_player_attendance(player_id, present)` | สลับ waiting ↔ absent |
| `cancel_play_day(session_id)` | ยกเลิกวันที่จองไว้แต่ไม่ได้ไป |

**ของเดิมที่ต้องแก้** — เปลี่ยนการเช็คสิทธิ์จาก `owner_id = auth.uid()` เป็น `can_edit_club(session.club_id)`:
`add_player`, `assign_court`, `start_match`, `substitute_player`, `cancel_match`, `finish_match`, `remove_court`, `update_court_hours`, `close_session`

**ของเดิมที่ตัดทิ้ง**: `get_or_create_my_session`, `open_session` — แนวคิด "ก๊วนที่เปิดอยู่ของฉัน" หายไป แทนด้วยการเลือกก๊วน → เลือกวัน

**`close_session` ยังคง freeze ยอดลง `final_*` เหมือนเดิม และยังต้องปฏิเสธเมื่อมีเกมค้าง** — ไม่เปลี่ยนหลักการนี้

## 6. สูตรคิดเงิน — ไม่เปลี่ยน

```
court   = Σ(courts.hours) × sessions.hourly_rate
shuttle = sessions.shuttle_count × sessions.shuttle_price
each    = (court + shuttle) / จำนวนคนที่ paying และ status ≠ 'absent'
```

เปลี่ยนแค่ตัวหาร: ต้องตัด `absent` ออก ทั้งใน `v_billing_summary` และใน `BillingPanel.jsx` ที่คำนวณซ้ำฝั่ง client — สองที่นี้ต้องตรงกันเสมอ

## 7. UI ใหม่

ตอนนี้ไม่มี router เลย ต้องเพิ่ม `react-router-dom` (ไม่มีทางเลี่ยงเมื่อมี 3 ระดับ)

```
/                        รายการก๊วน (ก๊วนของฉัน + ก๊วนที่ถูกแชร์มา)
/master                  ข้อมูลหลัก — แท็บ: ผู้เล่น | สนาม | ยี่ห้อลูกแบด
/club/:clubId            หน้าก๊วน — แท็บ: วันเล่น | สมาชิกก๊วน | สรุปรวม
/club/:clubId/day/:id    หน้าจัดลงคอร์ต (ของเดิมทั้งหมดย้ายมาอยู่ตรงนี้)
```

**หน้าก๊วน แท็บ "วันเล่น"** = สิ่งที่คุณขอ — แบ่งสองกลุ่ม: *กำลังจะถึง* (planned, เรียงวันใกล้สุดก่อน) และ *ที่เล่นไปแล้ว* (done พร้อมยอดที่ freeze ไว้ + จำนวนเกม) กดเข้าไปดูสรุปย้อนหลังได้

**ฟอร์มสร้างวันเล่น** — ตามลำดับที่คุณวางไว้ แต่รวมเป็น **หน้าเดียว ไม่ใช่ wizard 6 จอ** และ prefill จากวันล่าสุดของก๊วนนั้นทุกช่อง:

1. วันที่ + เวลา
2. สนาม (จาก master) → เลือกคอร์ตที่จอง + ชั่วโมงรายคอร์ต
3. ผู้เล่น (เลือกหลายคนจาก master + เพิ่มแขกได้)
4. ยี่ห้อลูกแบด (จาก master)
5. ราคาสนาม/ชม. + ราคาลูก/ลูก — **กรอกทีหลังได้ ปล่อยว่างไว้ก่อนได้**

เหตุผลที่ให้ราคาเว้นว่างได้: ราคาจริงมักรู้ตอนจบวัน ถ้าบังคับกรอกตอนสร้างจะได้ตัวเลขมั่ว แล้วไม่มีใครกลับมาแก้ ตอนกด "จบการเล่น" จะเตือนถ้ายังไม่ได้กรอกราคา

**หน้าวันเล่น** = ของเดิม (คิว, คอร์ต, ประวัติ, บิล) + แถบบนบอกวันที่/สนาม/สถานะ + ปุ่ม "เริ่มวันนี้" ถ้ายัง planned + ปุ่ม "จบการเล่นประจำวัน" ถ้า playing

**ก่อนเริ่มเล่น** มีรายการเช็คชื่อ กด "ไม่มา" ได้ และเพิ่มแขกหน้างานได้ตลอด

## 8. ลำดับการทำ

| เฟส | ได้อะไร | สถานะ |
|---|---|---|
| 1 | `schema.sql` + `functions.sql` ใหม่ทั้งชุด | ✅ เขียนเสร็จ — **ผู้ใช้ยังต้องรันเองใน SQL editor** |
| 2 | Router + หน้า `/master` ครบ 3 แท็บ | ✅ |
| 3 | หน้ารายการก๊วน + หน้าก๊วน + แท็บวันเล่น + ฟอร์มสร้างวันเล่น | ✅ |

**ยังไม่ได้ทดสอบกับฐานข้อมูลจริงเลย** — โค้ดผ่านแค่ `npm run build` กับ `npm run lint`

## 9. กฎเดิมที่ยังต้องรักษาไว้ทั้งหมด

- logic จับคู่อยู่ใน `src/utils/pairing.js` แบบ pure — ไม่แตะ ไม่ย้าย
- components ไม่ import `supabase` ทุกการอ่าน/เขียนอยู่ใน hooks
- อะไรที่แตะหลายตาราง = RPC หนึ่งทรานแซกชัน
- `refetchAll()` ทีเดียวแล้ว realtime เรียกซ้ำ ไม่ diff state ทีละแถว
- ปิดวันเล่นแล้วยอด freeze ห้ามคำนวณสดย้อนหลัง
- การหารเงิน = หารเท่ากันทุกคนที่มา ไม่หารตามเกมหรือตามนาที
- Realtime ต้องเปิดให้ `players`, `courts`, `matches`, `match_players` ใน dashboard

## 10. สิ่งที่ยังไม่ทำในรอบนี้

- เชิญคนที่ยังไม่มีบัญชีเข้าก๊วน (ต้องสมัครเองก่อน)
- ผู้เล่นล็อกอินมาดูสถิติตัวเอง (ตอนนี้ทุกอย่างมองจากฝั่งคนจัดก๊วน)
- แก้ชื่อ/ราคาของวันที่จบไปแล้ว (ตั้งใจล็อก ถ้าต้องแก้จริงต้องมีทางออกที่ตั้งใจออกแบบ ไม่ใช่เปิดให้แก้เฉยๆ)

lint error 3 อันของ `react-hooks/set-state-in-effect` **แก้หมดแล้ว** ระหว่างทาง — hook ใหม่ทุกตัวใช้ pattern
โหลดข้อมูลใน async function พร้อม flag `alive` ส่วน `useBadmintonData` ใช้ `mountedRef` เพราะ `refetchAll`
ถูกเรียกจาก realtime callback ด้วย ซึ่งอาจมาถึงหลัง unmount

## 11. รายการทดสอบหลังรัน SQL

**ตั้งค่าก่อน:** Supabase Dashboard → Authentication → Providers เปิด Email (จะเปิด Confirm email หรือไม่ก็ได้)
และ Database → Replication เปิด Realtime ให้ `players`, `courts`, `matches`, `match_players`, `sessions`

1. สมัคร → เข้าสู่ระบบด้วยรหัสผ่าน → ลืมรหัสผ่าน → ตั้งรหัสใหม่จากลิงก์ในอีเมล
2. สร้างก๊วน → เพิ่มผู้เล่น/สนาม/ยี่ห้อลูกในหน้าข้อมูลหลัก
3. สร้างวันเล่นวันนี้ → กดเริ่ม → จัดคนลงคอร์ต → จบเกม → คิวต้องวนอย่างเป็นธรรม
4. **กด "ไม่มา" แล้วตัวหารค่าใช้จ่ายต้องลดลง** และคนนั้นต้องหายจากคิว
5. **สลับตัวตอนเกมยัง pending แล้วคนที่ถูกสลับออกต้องไม่ได้ +1 เกม**
6. กดจบวันตอนยังมีเกมค้าง → ต้องถูกปฏิเสธพร้อมข้อความไทย
7. จบวันแล้วไปแก้ราคาสนามใน master → ยอดของวันที่จบแล้วต้องไม่ขยับ
8. สร้างวันในอนาคต → ต้องขึ้นในหัวข้อ "ที่จะเล่น" และเริ่มทีหลังได้
9. เริ่มวันที่สองทั้งที่วันแรกยังไม่จบ → ต้องถูกปฏิเสธ
10. แชร์ก๊วนให้อีกบัญชี → บัญชีนั้นต้องเห็นก๊วนในรายการ และ viewer ต้องแก้อะไรไม่ได้
